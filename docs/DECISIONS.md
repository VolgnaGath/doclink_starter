# Журнал решений — DocLink

Датированные решения и уточнения к ТЗ. **ТЗ — база и не отменяется этим файлом.** Если решение
расходится с ТЗ, действует ТЗ, а расхождение фиксируется в `CONTEXT.md` как открытый вопрос.
Изменение ТЗ допускается только отдельным решением и отдельным коммитом с префиксом `TZ:`.

## 31.10.2026 — согласованные решения по методу

- **Схема работы:** загрузка → извлечение LLM → карточка заполняется автоматически → поиск договоров → рекомендация →
  подтверждение бухгалтером. Бухгалтер может исправить карточку, после чего поиск запускается заново.
- **Вид и дата** берутся из карточки, заполненной извлечением (LLM; в варианте «без LLM» — регулярки). Эталон методу
  не подставляется. Нет вида или даты — исход «разбор», выдуманное значение не подставляется.
- **Единое правило дат:** кандидат — договор того же клиента с датой (из карточки) не позже даты документа. Без допуска.
  `registered_at` — только аудит.
- **Цель — только договор.** Косвенных путей (через допсоглашение или счёт) в v1 нет: каждый документ сопоставляется с
  договорами напрямую; при недостатке оснований — разбор.
- **Все связи подтверждает бухгалтер.** Очередь содержит все обработанные документы: рекомендации, разбор, «нет
  кандидата», ошибки. В `links` только `confirmed`/`manual` со ссылкой на `review_actions`.
- **Тип 8 по ссылкам:** две отдельные ссылки, каждая однозначно указывает на свой договор → две рекомендации; одна ссылка
  и два подходящих договора → альтернативы, не рекомендация; три и более договора → ручной разбор.
- **Номер и дата одной ссылки** оцениваются вместе. Есть явная ссылка с номером, а договору не соответствует ни одна →
  противоречие: только разбор с пояснением, не рекомендация. Номер: сырой 1,0; после нормализации OCR 0,9.
- **Ошибка обработки** (таймаут, невалидный ответ) после ограниченных повторов → статус «Ошибка обработки», можно
  повторить вручную. Документ остаётся в числе входов; при наличии эталонного договора — пропуск в Recall; в M не входит.
  Автоматического перехода на другой метод нет.
- **Метрики:** Precision = верные рекомендованные связи / все рекомендованные (M=0 → 0, M показывается, доля ошибок «—»);
  Recall = найденные верные / все эталонные связи; охват = документы хотя бы с одной рекомендацией / все входящие
  документы (включая без договора и ошибки; договоры-кандидаты не входят); «документ верно» = все нужные связи и ни одной
  лишней. Альтернативы для ручного выбора рекомендациями не считаются.
- **reference/linker.py** — вспомогательный материал, совпадение с ним не требуется. Правильность проверяется на
  fixtures с известным ответом (по одному на каждое правило выше).
- Исследования «ручной режим против assisted» нет; время подтверждения пишется в `review_actions`.

## 01.11.2026 — организация репозитория

- **ТЗ хранится в репозитории как `docs/TZ.md`** — конвертация `ТЗ.docx` от 31.10.2026 без изменения содержания.
  Оригинальный docx в репозиторий не входит, чтобы не дублировать документ.
- **Приоритет источников:** `docs/TZ.md` → `docs/DECISIONS.md` (только уточнения) → `CONTEXT.md` (состояние сессии)
  → `IMPLEMENTATION_STATUS.md` (статус этапов). Код и тесты — источник деталей реализации.
- **Работаем сразу в `main`:** без веток и pull request, пока нет CI. Каждое изменение коммитится и пушится
  в `origin/main` сразу после проверки.
- **Makefile обязателен:** повторяемые команды живут только в нём; актуальный список — `make help`;
  списки команд не дублируются в `AGENTS.md` и `README.md`.
- **`AGENTS.md` — только правила** (процесс, запреты, конвенции, навигация). История, бизнес-описания,
  дампы окружения, таблицы моделей и чеклисты этапов в нём не хранятся.
- **`CONTEXT.md` — память сессии:** состояние, доменные сущности, инварианты, открытые вопросы, следующий шаг.
  Обновляется в том же коммите, что и изменение, и не разрастается больше одного экрана.
- **Корпус коммитится в репозиторий:** 231 документ в оценке и 156 эталонных связей (real 16/9, synth 215/147).
  Корпус обезличен, таблица замен отсутствует.
- **`reference/` — только чтение:** скрипты не изменяются и не импортируются движком связывания.

## 01.11.2026 — API-first: этап «Контракт»

- **Новый этап 0 «Контракт»** перед каркасом: сначала TypeSpec-описание REST `/api/v1`, затем Docker и приложение.
  Старые этапы 0–7 сдвигаются в 1–8; изменение зафиксировано отдельным коммитом `TZ:`.
- **TypeSpec — дизайн-артефакт, не источник кодогенерации.** Пишем `.tsp` в `contract/`, компилируем в
  `contract/openapi/openapi.yaml` и коммитим артефакт. Pydantic-модели FastAPI пишутся руками; автоматическая
  проверка расхождений контракта с `app.openapi()` не вводится. Актуальность самого артефакта проверяет `make spec-check`.
- **Охват контракта на этапе 0 — только REST `/api/v1`** из ТЗ 4.5 плюс публичный `GET /health`. Схема БД, mock1c OData
  и внутренние сервисы в контракт не входят.
- **Авторизация API — cookie-сессия** (`session`), как у веб-входа; `/health` публичный.
- **Toolchain — host Node 22 LTS** и `package-lock.json`; Node не попадает в runtime-образ. Версии TypeSpec
  фиксируются точно, компилятор запускается целями `make spec`, `make spec-check`, `make spec-lint`.
- **Риск:** без drift-теста контракт может разойтись с FastAPI. Компенсация — `make spec-check` и ручная сверка
  при реализации этапа 1; при необходимости drift-тест добавляется позже отдельным решением.

## 01.11.2026 — уточнение этапа 2 «Документы и корпус»

- **Полный импорт:** 233 документа, из них 231 в оценке, 156 эталонных связей от 138 входящих документов.
  Оба исключённых real-документа сохраняются. Договоры-кандидаты не входят в знаменатель охвата.
- **Эталон:** `documents.gold` — объект с реквизитами, признаками наличия разметки, связями, трудными типами
  и происхождением. Он не заполняет рабочие реквизиты и справочник контрагентов; во вход движка не передаётся.
- **Версии:** повтор одинаковых данных и параметров возвращает существующую версию; изменения создают новую.
  Файлы дедуплицируются по SHA-256 отдельно от идентичности документов. До записи — валидация, запись БД — транзакционная.
- **Разбиение:** отдельно real/synth, сортировка сделок, новый `random.Random(seed)` для каждой части,
  первые `floor(N × tune_share)` перемешанных сделок — tune. Распределение сохраняется; сделка не разрывается.
- **Кандидаты:** все договоры соответствующей версии корпуса по клиенту и дате из карточки, независимо от split
  и сделки источника. Подбор порогов остаётся только на tune, итоговые метрики — только на test.
- **Противоречия корпуса:** 10 связей в synth_010/012/013/019/025 ведут к более поздним договорам.
  Импорт сохраняет их и выдаёт отчёт. Исправленная версия согласуется отдельно до замораживания протокола;
  правило дат не меняется. Входящих in-scope документов без договора в текущем корпусе нет.
- **Обезличивание:** пользователь подтвердил статус real и synth как обезличенных; импорт выставляет
  `is_anonymized=true`. Для пользовательских загрузок по умолчанию `false`; исходная таблица замен отсутствует.
- **Интерфейс:** этап 2 — один файл за раз, выбор/создание клиента (название обязательно, ИНН необязателен).
  Пользовательские клиенты отделены от клиентов корпуса. Множественная загрузка по Ф1 ТЗ и REST `/api/v1`
  реализуются на этапе 5; существующий контракт и конечное требование не меняются.
- **Ошибки текста:** оригинал сохраняется, пустой текст и сбой дают `error`. `stage_timings` вводится сейчас;
  каждая попытка содержит время и результат. Ручной повтор в карточке обрабатывает тот же документ синхронно,
  без автоматических повторов и без создания нового документа.
- Подробный план и проверки — `docs/plans/02-dokumenty-i-korpus.md`; реализация этапа ещё не начата.
