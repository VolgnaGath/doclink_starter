## 1. Общие сведения

- **Наименование:** подсистема установления связей между документами договорного процесса «DocLink».
- **Заказчик:** ООО «Дельта Игрек». **Разработчик:** автор ВКР.
- **Основание:** тема магистерской диссертации; задание на практику.
- **Назначение документа:** определяет функции, состав, данные, интерфейсы, требования к замерам и порядок приёмки прототипа.
- **Сроки:** прототип — до начала написания параграфа 2.3.

## 2. Назначение и цели создания

**Назначение.** Автоматическое извлечение реквизитов входящих документов клиентов (договор, дополнительное соглашение, счёт, акт, УПД), привязка каждого документа к договору как единой сущности сделки (связи «изменение», «основание», «исполнение») среди ранее зарегистрированных договоров того же клиента и передача бухгалтеру рекомендации или списка кандидатов. Каждую связь подтверждает бухгалтер; автоматическая запись связи без человека не предусмотрена. Вид, дата и клиент документа берутся из карточки и одинаковы для всех методов; вид, извлечённый LLM, оценивается отдельно.

**Цели:**

1. Сократить трудозатраты на заполнение карточек и поиск договора (таблица 1.3).
2. Обеспечить точность рекомендованных связей (для подтверждения в один клик) не ниже 0,98 (таблица 1.4).
3. Служить экспериментальным стендом: воспроизводимо сравнивать методы (правила, смысловой поиск, комбинированный) и модели, сохранять все замеры для параграфа 2.3.

## 3. Характеристика объекта автоматизации

Процесс AS-IS описан в параграфе 1.3: бухгалтер получает документ, загружает в «1С:Документооборот», вручную заполняет карточку и ищет договор. Поток около 1 700 документов в месяц, 25 % с неполной ссылкой. Живая 1С в прототипе заменяется загрузкой через интерфейс и заглушкой OData-сервиса.

## 4. Требования к системе

### 4.1. Требования к системе в целом

**Архитектура и развёртывание.**

- Один репозиторий на Python 3.12; запуск командой `docker compose up` на любой машине с Docker.
- Контейнеры: `api` (FastAPI + веб-интерфейс), `worker` (фоновая обработка), `db` (PostgreSQL 16 + pgvector), `mock1c` (заглушка OData), необязательный профиль `ollama` (локальная модель на CPU).
- Очередь заданий — таблица `jobs` в PostgreSQL с выборкой `FOR UPDATE SKIP LOCKED`; Redis не используется.
- Хранилище файлов — том Docker `/data/files`, путь по SHA-256 содержимого.
- Конфигурация — переменные окружения (`.env`), шаблон `.env.example`; ключи API только в `.env`, не в БД и не в логах.
- Миграции — Alembic; начальные данные (конфигурации моделей) — сид-скрипт.

**Надёжность.** Повторная обработка документа идемпотентна; ответы моделей кэшируются по хешу (модель + версия инструкции + текст), повторный прогон эксперимента не тратит деньги. Ошибка вызова модели — до 3 повторов с экспоненциальной задержкой, `затем статус «Ошибка обработки» (повтор вручную; документ остаётся в числе входов эксперимента, при наличии эталонного договора считается пропуском в Recall, в число рекомендаций не входит; автоматического перехода на другой метод нет)` с текстом ошибки.

**Безопасность.** Вход по логину и паролю (один пользователь из `.env`, сессия в cookie). Перед вызовом внешнего API текст обезличивается, если у документа нет признака «уже обезличен»; таблица замен хранится только в БД сервиса; ответ модели разобезличивается. Журнал всех вызовов моделей и всех решений.

### 4.2. Требования к функциям

**Ф1. Регистрация документов.**

- Загрузка PDF/DOCX/TXT через интерфейс (несколько файлов, выбор клиента).
- Импорт корпуса: архив `corpus/` с `documents.csv` и `links.csv` (формат текущего корпуса) — документы, эталонная разметка, разбиение на настроечную/тестовую часть по сделкам (seed задаётся).
- Коннектор к заглушке 1С: опрос `mock1c` раз в N секунд, забор новых документов.
- Схема работы: загрузка → извлечение LLM → автоматическое заполнение карточки → поиск договоров → рекомендация → подтверждение бухгалтером. Бухгалтер может исправить карточку, после чего поиск повторяется. Единое правило дат: кандидат — договор того же клиента с датой (из карточки) не позже даты документа, без допуска; дата регистрации хранится только для аудита. Если вид или дата не определены, документ идёт на разбор без подстановки значения.

**Ф2. Получение текста.** pdfplumber для текстового слоя, Tesseract (rus) для страниц без текста; сохраняются страницы, число символов, признак OCR, время.

**Ф3. Обезличивание.** Порт `anonymize_pdf.py::anonymize()`; согласованные замены в пределах клиента; обратная замена для ИНН и наименований в результатах извлечения.

**Ф4. Извлечение реквизитов (LLM).**

- Инструкция и JSON-схема из `prompts/extract_vN.txt` (версия сохраняется в каждом вызове). Начальная версия — из `run_models.py`.
- Поля: вид, номер, дата, контрагент (наименование, ИНН), сумма, предмет, ссылки на договор(ы), на допсоглашение, на счёт, цитаты-основания.
- Валидация Pydantic; при невалидном JSON — один повтор с сообщением об ошибке, затем запись с `valid=false`.
- Проверка цитат: каждая цитата должна находиться в тексте (нечёткий поиск); результат пишется в поле `evidence_ok`.
- Альтернативный извлекатель без LLM — регулярные выражения (`regex`, для абляции).

**Ф5. Эмбеддинги.** BGE-M3 (sentence-transformers, CPU) внутри `worker`, вектор 1024 в pgvector; модель кэшируется в томе. Резервный вариант — TF-IDF (для отладки без модели).

**Ф6. Установление связей.** Кандидаты — договоры того же клиента не позже даты документа; цель — только договор, косвенных путей через допсоглашение или счёт в версии 1 нет. Признаки: номер и дата **одной** ссылки вместе (номер сырой 1,0, после нормализации OCR 0,9, префикс 0,8, сходство 0,7), ИНН, наименование, смысловая близость; штрафы; оценка S; пороги τ_a и τ_r. Явная ссылка с номером, противоречащая договору, — только разбор с пояснением. Тип 8: две отдельные однозначные ссылки — две рекомендации; одна ссылка и два подходящих договора — альтернативы; три и более — ручной разбор. Равные лидеры — разбор. Вид и дата — из карточки (извлечение), одинаково для всех методов; эталон методу не подставляется. Веса и пороги — в конфигурации прогона. Базовые методы: `rules`, `semantic`.

**Ф7. Подтверждение.** Очередь содержит все обработанные документы с фильтром по исходу: рекомендация, разбор, нет кандидата, ошибка обработки. Каждая окончательная связь требует подтверждения. Карточка: текст, извлечённые поля (подсветка цитат, правка с повторным поиском), кандидаты с признаками, оценкой и пояснением расхождений; действия: подтвердить, выбрать другой, отклонить, указать вручную, повторить обработку. Фиксируется время от открытия карточки до решения.

**Ф8. Эксперименты.**

- Прогон = метод × конфигурация модели × эмбеддер × веса × пороги × часть корпуса.
- Подбор τ_a на настроечной части по условию Precision ≥ 0,98, применение на тестовой.
- Абляции одной кнопкой: без LLM-извлечения, без проверок, без смыслового поиска.
- Сравнение прогонов, выгрузка таблиц (CSV и Markdown) и графика «доля рекомендаций — доля ошибок» (PNG).
- **Проверка правильности:** набор fixtures с известным ответом (по одному на каждое правило Ф6 и на учёт ошибок в метриках). Совпадение с `linker.py` не требуется: скрипт — вспомогательный материал.

**Ф9. Учёт затрат и расчёт эффекта.**

- Стоимость вызова = токены × тариф конфигурации модели.
- Оценка «локального» времени для конфигураций с размещением `open-weights-cloud`: t = input_tokens / v_prefill + output_tokens / v_decode, где скорости — параметры конфигурации (для GPU 24 ГБ задаются допущением).
- Страница расчёта эффекта: входы — поток (табл. 1.3), время операций, ставка бухгалтера, доля рекомендаций (подтверждение в один клик) и доля ручного разбора, время подтверждения из review_actions из выбранного прогона, затраты на API или сервер; выход — часы и рубли в месяц, срок окупаемости, точка безубыточности N* = C_f / c.

### 4.3. Требования к замерам (для параграфа 2.3)

| Уровень | Что сохраняется | Таблица БД |
| --- | --- | --- |
| Вызов модели | провайдер, модель, назначение, версия инструкции, хеш входа, токены вход/выход, задержка, стоимость, статус, сырой ответ | llm_calls |
| Этап обработки документа | этап (text, anonymize, extract, embed, link), длительность, ошибка | stage_timings |
| Извлечение | все поля, валидность, проверка цитат, ссылка на вызов | extractions |
| Кандидат и решение | пара, тип, признаки, штрафы, оценка, ранг, решение, метод, прогон | link_suggestions |
| Действие бухгалтера | действие, выбранная цель, время на решение | review_actions |
| Прогон эксперимента | вся конфигурация, версия корпуса, seed, коммит, длительность, стоимость | experiment_runs |
| Метрики прогона | метрика × срез (всё, реальная, синтетика, трудные, тип 1–9, вид документа) | experiment_metrics |
| Кривая порога | τ, precision, recall, доля авто | threshold_curves |

Обязательные метрики: M — число рекомендованных связей; Precision = верные рекомендованные связи / M (при M = 0 Precision = 0, доля ошибок «—»); Recall = найденные верные связи / все эталонные связи; F1, в том числе на трудных; охват = документы хотя бы с одной рекомендацией / все входящие документы эксперимента (включая документы без договора и ошибки обработки; договоры-кандидаты не входят); доля документов, обработанных полностью верно (все нужные связи и ни одной лишней); доля на разбор; число ошибок обработки; Recall@3 кандидатов для разбора; точность извлечения по полям (вид, номер, дата, ИНН, сумма); среднее время и стоимость на документ; доля невалидных ответов; доля цитат, не найденных в тексте. τ_a — максимум охвата при Precision ≥ 0,98 и M > 0 на настроечной части; иначе статус NO_FEASIBLE_CONFIGURATION. Альтернативы для ручного выбора рекомендациями не считаются.
