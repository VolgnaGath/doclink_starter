не входит в базовый расчёт. 25% неполных ссылок не равны доле разбора алгоритма.

## 8.1. Методика и формулы

Подготовить `docs/EFFECT.md`: операции AS-IS/TO-BE, единицы, происхождение входов,
правила отбора замеров/расходов, формулы и условия отсутствия результата.

- Входы: поток, времена операций, ставка ₽/час, доли исходов выбранного прогона,
  время проверки карточки/подтверждения/разбора, переменные расходы на документ,
  постоянные расходы в месяц и разовые затраты внедрения.
- TO-BE включает человеческую работу для рекомендаций, разбора, отсутствия
  кандидата и ошибок. Для каждого исхода явно определить состав операций,
  чтобы полная длительность проверки не складывалась повторно с её частями.
- Подтверждение обязательно для каждой связи; две рекомендации на документ
  не превращаются в два документа. Ожидание API не считается автоматически
  рабочим временем бухгалтера.

Для времени в секундах и N документов, требующих связи:

```text
T_ASIS = сумма времён ручных операций с учётом частоты
T_TOBE = общее время операций + сумма(доля исхода × время его обработки)
Экономия часов = N × (T_ASIS − T_TOBE) / 3600
c = (T_ASIS − T_TOBE) × ставка / 3600 − переменные расходы на документ
Эффект в месяц = N × c − C_f
N* = C_f / c
Окупаемость, мес = разовые затраты / эффект в месяц
```

`C_f` — все постоянные месячные расходы выбранного сценария, включая явно
распределённую подготовку договоров. Для N* зафиксировать допущение о постоянных
удельных расходах и структуре потока при изменении N. При c≤0 нет конечной
точки безубыточности; при эффекте≤0 нет окупаемости. Неизвестное — null,
отрицательная экономия сохраняется. Без ставки доступны часы, но не денежный итог.

**Приёмка:** формулы однозначны, единицы согласованы, каждый вход имеет источник.

**Приёмка:** все данные прослеживаются до ID результатов/вызовов/действий;

## 8.3. Пользовательские замеры

До измерения зафиксировать состав копий и порядок работы. Создать рабочие копии
результатов выбранного прогона. Пользователь проверяет документы и завершает
сессии; сохранить ID, исходы, число документов, среднее и медиану длительности.
Протокол исключения/выбора повторных сессий определить заранее; не отбирать
только быстрые или успешные подтверждения. Неизмеренные категории остаются
без оценки либо получают явно подписанное пользовательское допущение.

Исключать незавершённые, отредактированные и повторно обработанные исходные
замеры; причины и количества исключений показать. Две ссылки учитывать полным
временем проверки документа. Старые интерактивные приёмки не доказывают экономию
труда. Chromium проверяет интерфейс, замеры человека он не заменяет.

**Приёмка:** есть описанный набор человеческих замеров с происхождением;
при его недостатке показано отсутствие данных. Исследование manual vs assisted
не заявляется: эффект переносится на поток расчётным путём по §1.3.

## 8.6. Итоговая приёмка

На отдельном чистом стенде пройти раздел 6 ТЗ:

1. Запуск по README, миграции, seed, загрузка весов и импорт корпуса.
2. Fixtures, матрица методов/моделей и абляций, выгрузки таблиц/графика.
3. Единый сценарий: новый документ → обработка → предложение → подтверждение
   → связь в mock1c. Предыдущие раздельные приёмки — основание, но не замена
   проверки этого единого сценария.
4. Калькулятор на исходном сценарии, выгрузка, скриншоты и сверка расходов.

Для чистого стенда обеспечить проверяемый перенос реальных артефактов с
происхождением либо явно разрешённые новые облачные вызовы. Сохранённый отчёт
сам по себе не воспроизводит эксперимент. Regex-проверка не заменяет качество LLM.
Новый платный вызов — только при явном допуске и проверке остатка бюджетов;
лимиты автоматически не повышать, две старые ошибки YandexGPT не улучшать.

Проверки реализации: формулы/единицы/границы, отбор замеров, дедупликация расходов,
авторизация/форма/выгрузки, Chromium; make lint, make test, полный verify-test.
Миграции и spec/spec-check/spec-lint — при изменении соответствующих частей.
Повторяемые проверки, чистый стенд и генерацию материалов оформить целями Makefile.
